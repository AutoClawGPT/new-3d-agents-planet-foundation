# three.ws architecture inventory

Research date: 2026-09-22. Primary sources reviewed: the three.ws repository, its referenced package/docs pages, and the published `@three-ws/solana-agent` package. This is an integration inventory, not a recommendation to copy the entire monorepo.

## Executive summary

three.ws is an Apache-2.0 monorepo that combines a browser-native Three.js/glTF viewer, an embodied agent runtime, a skill registry, voice/emotion/memory features, MCP/REST surfaces, and optional Solana/EVM identity and payments. Basic viewing and much of the agent runtime can run in-browser; production persistence, LLM key proxying, databases, wallets, token launches, paid endpoints, and GPU generation require server-side infrastructure.

The reusable boundary is clear in the repository's structure: `walk-sdk`, `character-studio` (MIT fork), `solana-agent-sdk`/`@three-ws/solana-agent`, `x402-modal-sdk`, the published SDK/package directories, and selected skill folders are portable. The hosted product pages, `api/` handlers, database schema, Cloud Run services, production secrets, managed wallets, IPFS pinning, and `three.ws` route/identity data are not drop-in modules. [Introduction](https://github.com/nirholas/three.ws/blob/main/docs/introduction.md) · [Structure map](https://github.com/nirholas/three.ws/blob/main/STRUCTURE.md)

## Minimum stack implied by the sources

* Browser: modern WebGL 2, Three.js, GLTFLoader, glTF 2.0/GLB, Draco/KTX2/Meshopt, VRM, animation retargeting, Web Audio/microphone, and optional Web Components/React. The character studio uses React 19, Vite, and Vitest.
* Agent runtime: manifest (`manifest.json` plus instructions/avatar/skills), LLM provider adapter/key proxy, memory, voice I/O, emotion/blendshape events, skill registry, and protocol/MCP adapter. A skill has an instruction, animation hint, voice template, JSON Schema, and handler; the same registry can execute in-world and expose MCP tools. [skill system](https://github.com/nirholas/three.ws/blob/main/docs/agent-abilities/chapters/07-skills.md)
* Server: Node 18+ / npm workspaces, REST and MCP handlers, Postgres (the production runbook uses Neon), Redis, object storage (R2/GCS), auth/session/CSRF/rate limiting, and a secret manager. The production server is Express on Cloud Run and emulates the repo's filesystem API route table. [server README](https://github.com/nirholas/three.ws/blob/main/server/README.md)
* Compute: separate CPU/GPU workers for avatar generation/rigging/talking-avatar/video jobs; Cloud Build + Docker + Cloud Run, Cloud Scheduler for cron, load balancer/CDN/TLS, and Cloudflare Workers where edge MCP is needed. [GCP runbook](https://github.com/nirholas/three.ws/blob/main/docs/ops/gcp-production.md)
* Solana: `@solana/web3.js`, Pump SDK/programs, wallet adapter or server-side signer, Jupiter (if swaps are enabled), x402 exact payment verification, current Pump Token-2022/AMM instruction layouts, Jito protection where used, and an RPC provider. EVM identity/payment is separate (ERC-8004/x402).

## Token launch and tokenized-agent pattern

The product flow is: configure an agent/token, rehearse against a real cluster, upload/resolve token metadata, choose wallet and optional initial buy, build/sign/send a Pump launch, record the launch in an application table, and expose live market/graduation status. The three.ws economy docs describe the launch flow as Pump SDK/API backed, recorded in `pump_agent_mints`, with the four Pump skills covering create, trade, fee management, and tokenized-agent payments. [agent economy](https://github.com/nirholas/three.ws/blob/main/docs/agent-abilities/chapters/09-the-agent-economy.md) · [start-here launch surfaces](https://github.com/nirholas/three.ws/blob/main/docs/start-here.md)

Payment after launch is a distinct flow: create an invoice with token/mint, currency, amount, memo, and validity window; derive a deterministic invoice-ID PDA; have the buyer sign USDC/SOL payment; verify on-chain (HTTP verification plus RPC/log-scan fallback); reject duplicate or expired invoices before delivering service. The tokenized-agent SDK docs warn that legacy/current payment programs coexist, so detection must be explicit. [agent-payments skill](https://github.com/nirholas/agent-payments-sdk/blob/main/tokenized-agents/SKILL.md) · [three.ws payment description](https://github.com/nirholas/three.ws/blob/main/docs/agent-abilities/chapters/09-the-agent-economy.md)

This does not prove that a new project may copy all launch code safely: Pump program instructions/IDLs and SDK versions change. Pin versions, run devnet rehearsal, inspect transaction simulation, enforce slippage/fee caps, and require an explicit human approval/risk acknowledgement for real funds. The repo's vendored Pump reference itself says it is a snapshot and must be re-vendored from upstream rather than edited. [Pump reference](https://github.com/nirholas/three.ws/tree/main/docs/pumpfun-program)

## Isolation, keys, and security

The safe pattern visible in the sources is:

1. Browser receives public manifests/avatars and short-lived session/API tokens only. The basic viewer needs no key; an LLM `key-proxy` injects provider keys server-side. [introduction](https://github.com/nirholas/three.ws/blob/main/docs/introduction.md)
2. Each tenant owns an explicit user/agent ID; every DB query, skill invocation, wallet operation, file/object path, and event stream is authorized against that identity. Owner-only wallet APIs, CSRF gates, and per-agent rate limits are documented. [wallet API](https://github.com/nirholas/three.ws/blob/main/docs/agent-wallet-api.md) · [marketplace security](https://github.com/nirholas/three.ws/blob/main/docs/marketplace.md)
3. Server-side secrets live in Secret Manager/KMS/HSM-backed storage where possible; encrypted agent wallet material is decrypted only in a narrowly scoped signer path, audited, TTL-cached if necessary, and never returned to the model/browser. The production docs show Secret Manager for worker secrets and separate runtime service accounts. [agent-sniper runbook](https://github.com/nirholas/three.ws/blob/main/workers/agent-sniper/README.md)
4. Every fund-moving action goes through allowlists/policy, spend caps, slippage/MEV limits, simulation, anomaly/freeze/kill switch, idempotency, and audit logging. The public docs describe a seven-layer transaction guard and owner-only guard controls. [start-here controls](https://github.com/nirholas/three.ws/blob/main/docs/start-here.md) · [guard API](https://github.com/nirholas/three.ws/blob/main/docs/agent-wallet-api.md)

Important caveat for a new multi-user app: `character-studio/.env.example` lists `VITE_HELIUS_KEY`, which would be a browser-exposed key if used directly. Treat that as an integration warning; proxy RPC/server validation and use per-tenant quotas. Do not put Helius/Jupiter keys, RPC credentials, API keys, seed phrases, or private keys in `VITE_*`, manifests, prompts, client bundles, or chat. [character studio configuration](https://github.com/nirholas/three.ws/blob/main/character-studio/README.md)

For the requested “unique API key/barrier key per user”, the sources provide primitives (owner session, API keys, auth, policy) but do not establish a complete tenant-key product contract. The new system should define a tenant record, hashed/revocable key IDs, scopes, expiration/rotation, quotas, audit events, and an authorization middleware that binds `tenant_id → agent_id → wallet_id → secret reference`. Never use a single shared barrier key as the isolation boundary.

## 3D/avatar/voice capabilities

The core body is a glTF/GLB avatar with optional rig metadata; the runtime supports Draco/KTX2/Meshopt and retargets humanoid clips. Character Studio exports optimized GLB/VRM, preserves blendshapes where present, previews animation, and sends an ArrayBuffer to its host iframe. The emotion system drives ARKit-style blendshape names when available. [character studio](https://github.com/nirholas/three.ws/blob/main/docs/character-studio.md)

Voice is not just a lip-sync widget: the published structure maps `@three-ws/voice` to ASR, TTS, and audio2face visemes, while the runtime associates speech/results with animation and mood. Face/viseme quality depends on the GLB's blendshape targets and the selected voice/ASR/TTS service. [package map](https://github.com/nirholas/three.ws/blob/main/STRUCTURE.md) · [skills runtime](https://github.com/nirholas/three.ws/blob/main/docs/agent-abilities/chapters/07-skills.md)

## Testing and deployment approach

The repository's development gate is `npm run setup`, then `npm run typecheck`, `npm run test:core`, `npm test` (Vitest + Playwright E2E), and `npm run audit:docs`; Character Studio has its own `npm run test:run` and lint/build scripts. [contributing](https://github.com/nirholas/three.ws/blob/main/CONTRIBUTING.md) · [studio tests](https://github.com/nirholas/three.ws/blob/main/character-studio/README.md)

Production is not a single frontend deploy: build the SDK/avatar artifacts in dependency order, build the Vite site, run generated-page/DB gates, build a Docker image, deploy the Express API to Cloud Run, sync Cloud Scheduler cron jobs, purge CDN, then smoke test live routes. Auxiliary GPU/long-running workers deploy independently. State kept in process memory requires single-instance affinity or external state. [GCP runbook](https://github.com/nirholas/three.ws/blob/main/docs/ops/gcp-production.md) · [workers README](https://github.com/nirholas/three.ws/tree/main/workers)

## License and integration risks

* Core repository: Apache-2.0. Character Studio explicitly incorporates an MIT-licensed upstream fork; preserve attribution and inspect each asset/model/license independently. [LICENSE](https://github.com/nirholas/three.ws/blob/main/LICENSE) · [Character Studio README](https://github.com/nirholas/three.ws/blob/main/character-studio/README.md)
* Do not assume every item in `awesome/`, model checkpoint, avatar/animation asset, vendor API, Pump SDK, or external skill is Apache/MIT or commercially reusable. Audit licenses and terms before shipping.
* Hosted-only assumptions include the three.ws database/schema, route table, production origins, GCP project/IAM, R2/GCS buckets, IPFS pinning, platform wallets, service URLs, cron secrets, and branded CDN URLs.
* Solana/Pump is real-money software: SDK/program version drift, Token-2022 and graduated AMM routing, duplicate invoice handling, transaction-size/versioned transaction fallback, RPC outages, and MEV/slippage are launch blockers to solve before production.
* `@three-ws/solana-agent` exposes powerful signing/actions but does not replace tenant auth, approval UX, policy checks, budget enforcement, or secure custody. Prefer browser wallet/non-custodial mode until a reviewed signer service exists.
* “100% identical” behavior cannot be inferred from docs or a hosted preview. Reproduce contracts with local tests, devnet rehearsal, browser E2E, transaction simulation, and production smoke/observability before enabling mainnet or autonomous launches.

## Recommended integration order

1. Reuse the viewer/manifest/skill contracts and Character Studio export path.
2. Add server-side LLM/RPC proxy and tenant-scoped auth/key middleware.
3. Add wallet adapter in non-custodial mode; implement policy/approval/audit before any autonomous signer.
4. Add Pump create/swap/fee/payment skills behind devnet rehearsal and dual-program detection.
5. Add x402 buyer/seller flows and receipts, then background workers/Cloud Run only for workloads that need them.
6. Port only the relevant tests/contracts and perform license, threat-model, browser, and on-chain verification before production.
