# Solana protocol source registry

Research date: 2026-09-22

Scope: primary Solana sources named in the project brief. This is a source map for architecture and implementation decisions; it is not a license to copy hosted products or to enable mainnet execution. No repositories were cloned, no packages were installed, and no credentials were used for this research.

## Decision key

- **Adopt** — use as a direct source of truth or a bounded integration after version/security review.
- **Research** — useful for a later decision; do not make it a dependency yet.
- **Defer** — marketing, waitlisted, incomplete, or not needed for the first vertical slice.

## Cross-cutting constraints for the platform

These constraints apply even when a source is marked Adopt:

1. Authenticate every request to a tenant/user identity from the server session. Never trust a client-supplied tenant ID, wallet address, registry identity, or “barrier key” as authorization.
2. API keys are per user/service, scoped to capabilities and environment, hashed at rest, expiring, revocable, rotatable, rate-limited, and shown only once. Provider keys (RPC, Helius, Jupiter, model, x402 facilitator) stay server-side.
3. Keep token launch as a capability workflow: intent → validation/allowlist → canonical transaction → simulation → exact preview/hash → explicit approval → signature verification → idempotent submit → confirmation/audit.
4. Freeze and hash the exact transaction message before requesting a signature. Reject altered bytes, unexpected signers, program IDs, writable accounts, recipients, fees, slippage, or cluster.
5. Default to local validator/Devnet. Mainnet is a separately configured environment with stronger limits, clear network labels, kill switch, audit trail, and legal/security sign-off.
6. An agent registry, x402 payment, reputation record, MCP endpoint, or SDP custody wallet is not by itself permission to execute arbitrary instructions. Every write passes the same policy and audit boundary.
7. Record source URL, retrieval date, package/repository revision, and the decision (adopt/research/defer) in the project ADRs. Re-check unstable docs before implementation.

## Explicitly unavailable or unverified in this pass

- `https://solana.com/SKILL.md`: linked and corroborated by the official `llms.txt`/skills page, but the research browser rejected the raw `text/markdown` content type; exact file contents were not rendered here.
- `https://solana.com/llms-full.txt`: officially referenced by `llms.txt`, but the research browser returned an internal error for the raw full-corpus endpoint; fetch/checksum it separately before mirroring.
- The Agent Registry page describes the protocol but does not, on the page inspected, provide the complete program ID, registration-file schema, SDK, deployment status, or security audit. Treat integration details as unverified until the registry's canonical technical docs/repository are located.
- The SDP landing page describes capabilities but presents a waitlist. Public API access, endpoint stability, pricing, custody/security attestations, and production eligibility are not established by that page.
- No claims about three.ws, ClawPump, Pump.fun, GMGN, SendAI, MediaPipe, LangGraph, Pay.sh, or any other third-party project are made in this registry; they require separate primary-source/license/security review.

## Source handling rule

This registry is a decision index, not a dependency lockfile. Before implementation, open the specific canonical source again, record the version/revision, read the applicable skill fully, and write a small acceptance test. Reuse ideas and compatible APIs only after license and supply-chain review; do not clone or install every linked repository into the product.
